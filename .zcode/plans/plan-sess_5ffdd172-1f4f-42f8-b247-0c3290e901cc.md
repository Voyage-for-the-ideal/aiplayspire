# 宝箱 open/skip 价值网络决策（Cursed Key 感知）

## 目标与关键结论

现状：`action_mixin.py:98-106` 对 CHEST 屏硬编码自动打开；持 Cursed Key 时每个普通宝箱 = 1 张随机诅咒。目标：持钥匙时用价值网络对比「打开（对随机结果取期望）」与「离开（拿 0）」，其余场景保持现行为。

探索确认的两个事实决定了方案形态：
1. **跳过宝箱零协议成本**：`{"type":"proceed"}` → `ChoiceScreenUtils.pressConfirmButton()`（`ChoiceScreenUtils.java:810-813`）→ 点击 ProceedButton → 打开地图离开房间，宝箱不开、`AbstractChest.open()` 不执行、诅咒不触发（`ProceedButton.java:179-182`）。不需要在 choice_list 里加 "skip"。
2. **决策时内容已半定**：`randomizeReward()` 在进房时消耗 `treasureRng`，`chest.goldReward`（bool）与 `chest.relicReward`（COMMON/UNCOMMON/RARE）public 字段已固定（两者可同时为真，同一次 roll 决定）。打开时才掷的只有：具体遗物（档位池均匀）、具体诅咒（10 选 1 均匀，`CardLibrary.getCurse()`，排除 AscendersBane/Necronomicurse/CurseOfTheBell/Pride）、金量 ±10% 抖动。

## 变更 1：StSCommunicationMod（Java，最小改动）

- `chest_boss`：`room instanceof TreasureRoomBoss`
- `chest_gold_reward`：`chest.goldReward`
- `chest_gold_amount`：GOLD_AMT（25/50/75，按 Small/Medium/Large；无金则为 0）
- `chest_relic_tier`：`"common"/"uncommon"/"rare"`（由 `chest.relicReward` 映射；无则 null）

 chest 可能为 null（onPlayerEntry 前），需判空。抽一个 package-visible 纯函数 `buildChestInfo(boss, goldReward, goldAmount, relicReward)` 返回 Map，便于无游戏启动的单测（`MapProtocolFieldsTest` 同款模式）。

- 测试：新增 `ChestProtocolTest`（纯逻辑：字段映射、判空、boss 标记）。
- 版本：`ModTheSpire.json` 1.4.3 → **1.5.0**（新功能 minor），description 追加宝箱字段说明；同步更新 `StSCommunicationMod/README.md` 的 `/state` 字段表与 changelog。

## 变更 2：sts_ai_framework（决策逻辑）

1. `models.py`：`GameState` 增加 4 个可选字段（默认 None，向后兼容旧版服务器）。
2. `event_pools.py`：
   - `CHEST_CURSE_POOL` 常量：Clumsy/Decay/Doubt/Injury/Normality/Pain/Parasite/Regret/Shame/Writhe（均匀 1/10，ID 与 inference.py 现有诅咒集合同一大小写规范）。
   - `chest_relic_pool(tier, character, owned_ids)`：common/uncommon/rare 三档静态遗物表，从 `cardcrawl/helpers/RelicLibrary.java` 的分档列表编译，仿现有 `relic_pool()` 的 character/owned 过滤。
3. `decision_mixin.py` 新增 `_handle_chest(state)`（放在 `_rank_bonfire_targets` 附近，复用 `event_state_payload` / `_apply_choice` / `evaluate_state`）：
   - **短路**（保持现行为，零 V 调用）：`chest_boss` 为真、未持 Cursed Key、或 `value_engine is None` → 直接走现有 auto-open 路径。理由：无诅咒时打开严格占优（还能解锁蓝钥匙链接选项）。
   - **打分**：`skip = V(payload(state))`；`open = max(relic 期望, 蓝钥匙期望（若 keys.sapphire 为假）)`。
     - 遗物期望：枚举 `chest_relic_pool(chest_relic_tier) − owned` × `CHEST_CURSE_POOL`，每分支 `composite_event`（`gain_gold`（若 gold_reward，取 GOLD_AMT 基数）+ `obtain_relic` + `add_card(诅咒)`）→ 权重 1/N 均匀 → 期望。分支超 ~400 时先按 `V(S+r)` 取遗物 top-K（K≈24）预筛（向上偏差，注释注明）。
     - 蓝钥匙期望：对 10 诅咒取 `V(S + sapphire + curse)` 均值——诅咒在 open() 开头就结算，事后换钥匙照样吃；拾取后的遗物 vs 蓝钥匙选择仍由现有 `_should_take_sapphire_key` 处理，此处只做选项价值上限 credit。
     - Omamori：`_apply_choice` 现有逻辑已按 `relic_states` 计数拦截诅咒，期望自然正确。
   - `log_event(event="chest_decided", floor=..., choice=..., value=..., noop=..., branches=N)`（仿 `event_decided`，`decision_mixin.py:583-591`）。
   - 返回：open → `CHOOSE 0`；skip → `can_proceed` 为真给 `PROCEED`，否则 `WAIT` 等下轮轮询。
4. `action_mixin.py:98-106`：CHEST 块改为调用 `self._handle_chest(state)`（含原 fallback 逻辑）。
5. `selectcard/src/inference.py` 小修：`_should_block_curse_add` 的诅咒集合补上 Decay/Parasite（真实 Omamori 拦截任意诅咒，现集合漏了这两个，会导致持 Omamori 时期望偏悲观）。

## 变更 3：测试

新增 `sts_ai_framework/tests/test_chest_decision.py`（用 `test_structured_events.py` 的 `make_state`/`Harness`/`FakeValueEngine` 模式）：
1. 未持 Cursed Key → CHOOSE 0，引擎零调用；
2. 持钥匙 + 引擎给 skip 高分 → PROCEED，且枚举的 effects 覆盖 10 诅咒 × 档位池；
3. 持钥匙 + open 高分 → CHOOSE 0；
4. `chest_boss=True` → 无条件 CHOOSE 0；
5. `value_engine=None` → 回落 auto-open；
6. skip 决策 + `can_proceed=False` → WAIT；
7. 持 Omamori（counter>0）→ 枚举分支无 `add_card` 生效。
另加真引擎测试（仿 `test_structured_effects_apply_without_text_parsing`，无 torch 则 skip）：`gain_gold + obtain_relic + add_card(Decay)` 应用正确、Omamori 拦截 Decay。
