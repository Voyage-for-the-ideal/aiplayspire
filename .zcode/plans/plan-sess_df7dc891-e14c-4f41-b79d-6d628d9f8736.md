## Part B：BattleAiMod 全败死亡路径兜底（fix，1.4.0 → 1.4.1）

**B1 纯函数判定**（`BattleAiController` 新增静态方法，可离线单测）：
`static StateNode noWinFallback(StateNode progressFallback, StateNode deathNode)` — 当 `progressFallback.parent == null`（即无任何进展、原逻辑会下发空路径）且 `deathNode != null` 时返回 `deathNode`，否则返回 `progressFallback`。

**B2 两处终局兜底接入**：
- `step()` 的 SEARCH_EXHAUSTED 分支（`BattleAiController.java:247-256`）：`committedTurn == null` 时经 `noWinFallback` 取 deathNode；**命中死亡路径时必须显式 `shouldReplan = false`**（不能沿用 `hasProgress(bestEnd)`——deathNode 有 parent 链会误判为 true 导致客户端无限重规划）、`stopReason = "ALL_LOSE"`、`battleComplete = false`，并打印 System.err 说明。
- `finishWhenBudgetReached()`（`:422-449`）：`partialResult == null`（bestTurn/backupTurn/committedTurn 全空）时同样处理。
- 有部分进展的场景（committedTurn/bestTurn 存在）**保持现状**（回放+重规划），最终会收敛到上述无进展终局，由死亡路径兜底收尾。
- 只在无进展终局启用是刻意的：此时客户端必然是全新 runner（`sendState()` 置 `rerunController=null`，AiClient.java:144），死亡路径不存在前缀分歧风险，不消耗 replay 重试预算。

**B3 正确性要点**（已走查确认，实现时复核）：
- deathNode 命令列表 = `[null(根占位), c1..cM]`（`AiServer.java:394-399`），与胜利路径同构；客户端对 null 命令跳过不执行（`CommandRunnerController.java:67-76`），不会 NPE。
- StateDiffChecker 只在每条命令**执行前**比对预录 diff（死亡后无后续命令，不会误触发 mustRestart）。
- 客户端死亡走原版 DeathScreen（BattleAiMod 的 DeathScreen patch 仅 isServer 拦截）；`isInARun()` 下降沿触发 1.4.0 的 `resetRunState()`；框架收到 GAME_OVER 后自动重开——链条闭环。
- 实现时验证死亡状态的 `saveState.jsonEncode()`（AiServer 的 endFileName/final_state_key 写入，`AiServer.java:205-220`）不抛异常；若异常仅对该写入加 try/catch 降级，不影响命令下发。

**B4 单元测试**：`scumthespire/src/test/java/battleaimod/BattleAiControllerFallbackTest.java`（junit4；StateNode 构造器为纯字段赋值，可传 null controller 离线构造链）：无进展+有 deathNode → deathNode；无进展+无 deathNode → 原 fallback；有进展 → 原 fallback（即使有 deathNode）。
